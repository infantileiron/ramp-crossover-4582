# 岔路导览 · 坡道指引交叉测试

青栈导览小组用同一条坡道试走两轮，比较文字箭头牌与坡道图标牌，留下一份可复核的标牌调整建议。

## 现场背景

青栈导览小组是一个模拟的 8 人公共空间导览团队。此前，现场计时员在两张表里手记第 1、2 轮用时，分析员在共享表格里按编号拼接，复核员通过群消息确认后续安排。主要问题是缺测容易错配，第二轮更熟悉路线容易被归功于某块标牌，发布时也难以追溯用的是哪版参数和台账。

上游提供匿名参与者编号、指定顺序和实测秒数。本项目替代两轮台账拼接、对照计算和结论留档。下游场务通过发布报告和 CSV 安排补测或局部试挂。演示路线 **R07 北门连廊坡道** 从北门入口经花坛岔口至连廊平台，全长 86 米。A 为文字箭头牌，B 为坡道图标牌。两轮使用换过牌的同一路线，从入口出发计时至到达平台。

| 角色 | 演示账号 | 演示密码 | 典型动作 |
|---|---|---|---|
| 业务复核员 `reviewer` · 程岚 | `reviewer` | `Review5215!` | 查看台账、参数版本和草稿，下载 CSV，发布带说明的现场建议 |
| 数据分析员 `analyst` · 沈栩 | `analyst` | `Analyze5215!` | 按人登记或补录两轮用时，建参数版本，提交运行，查看和下载草稿 |
| 观察员 `viewer` · 陶桥 | `viewer` | `View5215!` | 读路线和匿名台账，查看及下载已发布报告 |

## 一天的工作剧本

1. 08:40，沈栩登录，打开 R07 路线样书，确认 86 米的计时范围及 A、B 样牌。
2. 09:00，在配对台账检查 12 人。AB 序列 7 人登记、6 人完整。BA 序列 5 人登记、4 人完整。AB07 缺第 2 轮，BA05 缺第 1 轮。
3. 09:20，用「现场初核」版本运行，每序列至少 3 对，顺序差复核线为 8 秒。AB 组 67→49 秒，BA 组 71→73 秒。
4. 10:35，现场补交 AB08，依 AB 顺序两轮用时分别为 67 和 49 秒。将行录入台账。
5. 11:00，新增「二轮上牌复核」，将每序列门槛设为 4 对，复核线设为 10 秒。提交后，后台冻结 13 条台账记录。
6. 11:05，对照页显示 11 人完整。处理差估计为 −10 秒，时期差估计为 −8 秒，按人数汇总的变化为约 −10.73 秒。双轮均值顺序差为 +14 秒，达到复核线。下载 `ramp-report-2.csv`（连续完成上述两次运行时）。
7. 11:15，程岚复核后发布「补测后复核」，说明保留北门现牌，补齐 BA 序列的记录并在下一场试走延长换牌间隔。
8. 11:25，陶桥在报告档案中打开已发布的报告和 CSV，安排下一场计时。

## 时段分组与随机分派

现场还可按时段两人成组：每个时段先登记席位 1、席位 2 两位匿名参与者，系统在建立分组时**封存**一个随机顺序（谁先走 A、谁先走 B），对现场不可见。任一人开走时，系统才揭晓两人**相反**的顺序并**锁住整组**；此后不能再换人。开走前可随时换人，换人只改参与者编号，不改封存顺序。

- 开走与换人并发时，两者都在分组行上取行锁串行化。若换人先提交，开走请求会用客户端传来的人员编号与最新成员核对，旧成员的分派不会记到新人名下；若开走先提交，换人请求因整组已锁而被拒绝。
- 揭晓时若写库失败，整笔事务回滚、封存顺序仍留在分组行上；重试揭晓沿用同一顺序，不会改换已确认的分派。
- 只有已开走的分组进入分析快照；仍在待开走向的分组及其封存顺序不进入快照，避免提前泄露。

报告页新增「随机分派检验」：在每个原分组内互换两位成员的 AB/BA 顺序，枚举（分组数大时用固定种子抽样）全部随机分派，计算**图标收益（A−B，正值为图标牌更快）不低于实测值**的概率。概率越小，越不支持“图标牌并无优势、只是随机波动”的解释。已开走的分组只要有任一轮缺测（或成员/分派缺失），检验暂缓并逐项列明缺项，不影响已有人工配对台账的常规分析。

## 计算口径

输入是路线、不可变参数版本和提交时按顺序/编号排列的匿名试走快照。方法版本为 `crossover.two-period.v1`，对规范化 JSON 做 SHA-256。只分析两轮都有用时的同一参与者，按序列保留登记数、配对数和缺测编号，缺测不插补。每轮用时允许 0.01–900 秒，同一受试者每条路线一个编号且顺序固定。时段分组另存已揭晓的相反顺序与两位参与者用时，报告按分组互换顺序做随机分派检验（方法 `randomization.paired-order.v1`）。

定义 `Δ_AB`、`Δ_BA` 为各序列完整配对者的第 2 轮减第 1 轮的均值。`n_AB`、`n_BA` 为配对人数。

| 输出 | 公式与解释 |
|---|---|
| 总体变化 | `(n_AB × Δ_AB + n_BA × Δ_BA) / (n_AB + n_BA)`，按实际完整样本人数加权。仅描述这一轮切换前后合在一起的变化，两次观测无法判断长期趋势。 |
| 处理差估计 | `(Δ_AB − Δ_BA) / 2`，方向为 B−A。负值对应 B 较短。 |
| 时期差估计 | `(Δ_AB + Δ_BA) / 2`，方向为第 2 轮−第 1 轮。路线熟悉、疲劳、时段和人流均可能体现在共同变化中。 |
| 双轮均值顺序差 | BA 组两轮均值的平均 − AB 组两轮均值的平均。绝对值达到阈值即告警，同时报告两组配对人数是否不平衡。这个差可能来自组间基础差异、现场条件或延续影响。 |
| 首轮对照 | 完整配对者的 BA 第 1 轮均值 − AB 第 1 轮均值，作为组间描述保留。 |

两组等权可避免完整人数差异把时期影响混进处理差公式。处理与时期差作为探索性点估计，依赖可加的共同时期影响、组间可比和差异性延续影响可忽略等条件。仅两轮时，无法单独识别延续效应。这里只做现场诊断，没有区间估计或对缺测机制的校正。人工台账的顺序仍由现场分配；时段分组路径的分派随机性来自封存顺序与随分派检验，小样本结论用于安排复核与试挂。

每序列配对门槛可设为 2–50。任一序列不足时，处理差和时期差留空，仍保留可算的描述值。双轮均值差告警、人数不平衡或配对不足时，复核员可选择补测或保留现牌。局部试挂仅在两序列等人数、过门槛、无顺序差告警且 B 的估计用时较短时可选，仍需人工说明。每个结论都固定到运行快照。重跑使用原参数版的新快照，历史发布不会随台账更新。

## 启动和访问

在项目根目录执行。需要 Docker Desktop 或 Docker Engine 与 Compose。此批验收从批次根目录通过共享 `scripts/verify-project.sh gb-5215` 启动并清理。

```sh
cp .env.example .env
docker compose up --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

网页 `http://127.0.0.1:18284/`，API 文档 `http://127.0.0.1:19284/docs`，PostgreSQL 16 `127.0.0.1:17784`，监听地址均为回环。应用入口先执行 SQL 初始化，默认自动执行一次可安全重复的演示 seed。对冲突的自然键不覆盖现有记录。

| 组件 | 实现 |
|---|---|
| `frontend` | Nginx 1.27，代理 `/api/`，原生 HTML、CSS 和 JavaScript |
| `backend` | Python 3.11、FastAPI、Psycopg、JWT 与角色校验，写操作与审计同一事务 |
| `worker` | Python 后台进程，通过 PostgreSQL 锁领取快照，计算后原子写 CSV，轮询心跳用于健康检查 |
| `db` | PostgreSQL 16 Alpine，保存匿名台账、参数、报告和审计 |
| `redis` | Redis 7 Alpine，唤醒 worker。待算任务以数据库为准 |

本地开发时可用 `docker compose up --build --wait` 加载最新镜像，`docker compose logs -f backend worker` 查看运行输出，`docker compose down` 保留数据，或 `docker compose down -v --remove-orphans` 删除本项目的本机数据和导出卷。业务操作通过网页或 FastAPI 文档执行。

`.env.example` 包含 `COMPOSE_PROJECT_NAME`、`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT`、`NETWORK_SUBNET`、`POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB`、`JWT_SECRET` 和 `SEED_DEMO`。默认子网 `10.221.215.0/24` 可覆盖。`DATABASE_URL`、`REDIS_URL`、`EXPORT_DIR` 由 Compose 注入应用容器。三个命名卷分别保存 PostgreSQL、Redis 和后端/worker 共用导出。演示凭据和签名密钥用于本机演示。

目前页面针对一条已登记路线，样牌方案随路线一起初始化。新增路线与变更样牌由上游数据准备，无网页配置入口。CSV 包含算法原始量、门槛、摘要和匿名快照行。发布决定和人工说明保存在报告详情中。没有外部发布或真实标牌操作。

## 目录与枚举

- `backend/migrations/`、`backend/scripts/` 保存数据库初始化和种子；`backend/src/` 分路由、服务、配置、输入校验、记录模型、响应中间件和 worker。
- `frontend/src/` 保存访问层、会话状态、路由、页面、共享样牌/对照组件和格式化工具。源码与批次的 `test-artifacts/gb-5215/` 分开放置。
- 角色 `reviewer/analyst/viewer`、序列 `AB/BA`、报告状态 `queued/ready/failed/published`、决定 `retest/retain/pilot` 定义于 `backend/src/constants/domain.py` 和 `frontend/src/constants/domain.js`，数据库约束见 `backend/migrations/001_initial.sql`。角色用于鉴权与导航，序列用于配对记录和对照展示，状态用于队列与档案，决策用于后端复核及报告详情。
- 时段分组表 `field_session`、成员表 `session_member`、已揭晓分派表 `session_assignment` 见 `backend/migrations/002_sessions.sql`；服务在 `backend/src/services/sessions.py`，随机分派检验在 `backend/src/services/randomized.py`。
